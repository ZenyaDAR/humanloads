# План проекта

Название: **humanloads** («загрузки людьми»). На 2026-11-03 имя свободно на npm, на GitHub репозиториев с таким именем нет.
Одно имя на всё: репозиторий, npm-пакет (CLI), путь Pages `/<user>.github.io/humanloads/`.
Идея: страница пакета «как на npm», но рядом с официальными загрузками показана оценка реальных установок
и доказательства использования. Open source, хостинг на GitHub Pages, без бэкенда.

Как оцениваем, описано в [METHODOLOGY.md](METHODOLOGY.md).

---

## Архитектура

```
браузер ──► api.npmjs.org        (загрузки, по версиям)
        ──► registry.npmjs.org   (метаданные, даты публикаций)
        ──► packages.ecosyste.ms (зависимые пакеты/репо)      ← этап 2
        ──► data.jsdelivr.com    (CDN-хиты)                   ← этап 2
        ──► api.github.com       (звёзды, форки)              ← этап 2
```

- **Бэкенда нет.** Все API выше отдают `Access-Control-Allow-Origin: *` (проверено 2026-11-03),
  поэтому сайт целиком статический и считает всё в браузере пользователя.
- **Оценка — чистый модуль** `src/estimate.ts` без DOM. Его используют сайт, тесты и (позже) CLI.
- **Маршрутизация:** `https://<user>.github.io/humanloads/<pkg>` и `/@scope/name`.
  GitHub Pages не умеет SPA-роутинг, поэтому `index.html` копируется в `404.html` при сборке.
  Страница поднимается и читает `location.pathname`.
  ponytail: страница отдаётся со статусом 404. Для людей это незаметно, для SEO плохо. Если важен SEO, на этапе 4 перейти на пререндер популярных пакетов.
- **Деплой:** GitHub Actions → `actions/deploy-pages`. Отдельная ветка `gh-pages` не нужна, Pages берёт артефакт сборки.

## Структура репозитория

Один пакет, без монорепозитория. Сайт, CLI и скрипты Actions используют одно ядро.

```
humanloads/
├─ .github/workflows/
│  ├─ deploy.yml          # push в main: test → build → deploy-pages            (этап 1)
│  ├─ canary.yml          # cron раз в сутки: данные канарейки → public/data/    (этап 3)
│  └─ badges.yml          # cron: оценки для tracked.json → public/badges/       (этап 4)
├─ docs/
│  ├─ METHODOLOGY.md      # как считаем — главный документ для доверия
│  └─ PLAN.md
├─ public/                # копируется в сборку как есть
│  ├─ favicon.svg
│  └─ data/               # JSON, который коммитят Actions (канарейка, бейджи)
├─ src/
│  ├─ core/               # чистый TS: без DOM, работает в браузере и в Node
│  │  ├─ estimate.ts      # модель: сырые ответы API → оценка, диапазон, уверенность
│  │  └─ sources.ts       # fetch-обёртки над npm / registry / ecosyste.ms / jsDelivr / GitHub
│  ├─ web/
│  │  ├─ main.ts          # роутер: pathname → главная | страница пакета | 404
│  │  ├─ home.ts          # поиск + примеры
│  │  ├─ package.ts       # страница пакета
│  │  ├─ chart.ts         # линейный график на rough.js
│  │  └─ style.css        # цветовые токены, бумага, шрифты
│  └─ cli.ts              # npx humanloads <pkg>                                   (этап 4)
├─ scripts/
│  └─ fetch-fixture.mjs   # сохраняет ответы API пакета в test/fixtures/<pkg>/
├─ test/
│  ├─ fixtures/<pkg>/     # downloads.json, registry.json, versions.json
│  └─ estimate.test.ts    # node:test
├─ index.html
├─ vite.config.ts         # base: '/humanloads/', после сборки index.html → 404.html
├─ package.json           # scripts: dev, build, test; bin: humanloads (этап 4)
├─ tsconfig.json
├─ LICENSE                # MIT
└─ README.md
```

Правила:
- **Зависимости идут в одну сторону:** `web → core`, `cli → core`. `core` не знает о DOM и не импортирует ничего из `web`.
- **`estimate.ts` не делает сетевых запросов.** На вход ему подают уже скачанные данные. Поэтому тесты гоняют его на фикстурах без сети, а одна и та же функция работает и на сайте, и в CLI.
- **Тесты только для `core`.** UI проверяем глазами на 3–4 пакетах.
- Файлы, помеченные этапом, создаём только на этом этапе. Заготовки заранее не делаем.

## Технологии

| Что | Выбор | Почему |
|---|---|---|
| Сборка | **Vite** + TypeScript | Ноль конфигурации, `base` для Pages одной строкой |
| UI | **без фреймворка** (vanilla TS) | Одна страница и одна форма поиска, фреймворк тут лишний. Если страниц станет 5+ — Preact (3 KB) |
| Графики | **rough.js** | Рисует SVG «от руки», это и есть фирменный стиль. Свой линейный график на нём ~100 строк |
| Тесты | `node:test` | Встроен в Node, тесты только для `estimate.ts` на зафиксированных данных |
| Шрифты | Google Fonts | см. дизайн |

## Дизайн: «лабораторный блокнот»

Светлая бумага, графит и один яркий маркер. Метафора: исследователь размечает график npm карандашом
и обводит маркером то, что настоящее.

| Токен | Цвет | Назначение |
|---|---|---|
| `--paper` | `#FBF8F1` | Фон: тёплая бумага, лёгкая клетка через CSS `background-image` |
| `--ink` | `#2B2A28` | Текст, оси |
| `--pencil` | `#A9A39A` | **Загрузки npm**: полупрозрачная пунктирная карандашная линия |
| `--marker` | `#E8542F` | **Реальная оценка**: жирная линия маркером + штриховка диапазона |
| `--highlight` | `#FFE27A` | Выделитель под ключевыми цифрами |
| `--note` | `#3E6FD8` | Пометки на полях: «всплеск: v0.3.0 опубликована» |

Тёмная тема — «чертёжная доска»: `#1E2430` фон, мел вместо графита. Добавляем на этапе 4.

Шрифты: заголовки и пометки — **Caveat** (рукописный), текст — **IBM Plex Sans**, цифры — **IBM Plex Mono**.

## Этапы

### Этап 0 — проверка модели (1–2 вечера)
Задача: убедиться, что оценка вообще осмысленна, до того как рисовать сайт.
- [ ] `src/estimate.ts`: шаги A и B из методологии, на вход — сырые JSON трёх эндпоинтов.
- [ ] `scripts/fetch-fixture.mjs <pkg>`: сохраняет ответы API в `test/fixtures/<pkg>/`.
- [ ] Фикстуры: nervegraph, ваши остальные пакеты, 3 популярных (`react`, `lodash`, `zod`), 3 заброшенных.
- [ ] `test/estimate.test.ts`: на nervegraph органика за неделю попадает в диапазон 0–6; у `react` оценка ≥ 90% от npm.

**Готово, когда:** таблица «npm vs оценка» по фикстурам выглядит правдоподобно для всех трёх групп.

### Этап 1 — MVP-сайт (≈ неделя)
- [ ] Vite-проект, `base: '/humanloads/'`, копирование `404.html`, workflow деплоя в Pages.
- [ ] Главная: поиск (`registry.npmjs.org/-/v1/search?text=`), пара примеров-ссылок.
- [ ] Страница пакета: шапка (имя, версия, описание, лицензия, ссылки), две карточки чисел, график за 12 месяцев,
      пометки публикаций, разбивка «куда ушли загрузки», таблица по версиям, ссылка на методологию.
- [ ] Состояния: загрузка, пакет не найден, пакет без загрузок, ошибка/лимит API.
- [ ] Кэш ответов в `sessionStorage` (в try/catch), чтобы не долбить API при переходах.

**Готово, когда:** `https://<user>.github.io/humanloads/nervegraph` открывается и показывает «≈ 2–6 / нед».
Сразу после этого — пост на Reddit/HN/dev.to с вашим же графиком как примером. Это и есть тест спроса.

### Этап 2 — доказательства использования
- [ ] Блок «Кто реально пользуется»: зависимые пакеты (ecosyste.ms, со списком), зависимые репозитории, jsDelivr-хиты, GitHub-звёзды/форки.
- [ ] Индикатор уверенности (high/medium/low) с объяснением в тултипе.
- [ ] Ссылка «Найти упоминания на GitHub» → готовый запрос поиска по коду (`"\"<pkg>\"" path:package.json`).
      ponytail: просто ссылка, а не API. Поиск по коду требует токен. Добавить, когда кто-то попросит.

### Этап 3 — точность
- [ ] Пакет-канарейка + GitHub Action по cron раз в сутки: пишет его загрузки в `data/canary.json` в репозиторий.
      Сайт берёт оттуда глобальный пол и размер всплеска вместо констант.
- [ ] Сигнал «будни/выходные» в оценку уверенности.
- [ ] Расширить контрольную группу до 30 пакетов, тесты на регрессию модели.
- [ ] Версии модели (`model: v1/v2`) в интерфейсе и методологии, чтобы цифры можно было объяснить.

### Этап 4 — обёртки и распространение
- [ ] **Бейдж для README.** Shields.io `endpoint` читает JSON. Action по cron считает оценку для пакетов из
      `tracked.json` (добавляются через PR) и кладёт `badges/<pkg>.json` на Pages.
- [ ] **Сравнение** `/compare/a,b`: две оценки на одном графике (аналог npmtrends, но честный).
- [ ] **CLI** `npx humanloads <pkg>`: тот же `estimate.ts`, вывод таблицей в терминал.
- [ ] Тёмная тема, OG-картинка для шаринга, пререндер страниц популярных пакетов (SEO).
- [ ] Английская версия README и интерфейса (если проект пойдёт в массы, по умолчанию английский).

## Риски

| Риск | Что делаем |
|---|---|
| Лимит GitHub API 60 запросов/час без токена | GitHub-блок необязательный, при 403 скрываем. Опционально — свой токен в `localStorage` |
| ecosyste.ms медленный или лежит | Блок грузится отдельно и не ломает страницу |
| Модель ошибается, и автор пакета обижается | Всегда диапазон + уверенность + открытая методология + ссылка «оспорить» (issue) |
| npm меняет API | API стабилен с 2014 года. Ловим по тестам на фикстурах + ручной smoke |
